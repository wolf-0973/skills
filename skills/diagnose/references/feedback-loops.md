# 更多构造反馈循环的方式

`SKILL.md` Phase 1 的前四种（失败测试、curl 脚本、CLI + 快照 diff、headless 浏览器）不适用时，按这个顺序试。目标不变：一条已跑过、能对着这个 bug 变红、确定、秒级、agent 可跑的命令。

5. **重放抓下来的 trace** —— 把真实的网络请求 / payload / 事件日志存盘，隔离地重放进那条代码路径。适合「只在生产的某种输入下炸」。
6. **一次性 harness** —— 起系统的最小子集（一个服务 + mock 掉的依赖），用一次函数调用打到 bug 代码路径。适合整体启动太慢或依赖太多。
7. **property / fuzz 循环** —— bug 是「有时输出不对」时，跑 1000 个随机输入找那个失败模式。
8. **bisect 探测脚本** —— bug 出现在两个已知状态之间（commit、数据集、版本）时，把「切到状态 X、检查、重复」自动化成一条命令，交给 `git bisect run`。
9. **差分循环** —— 同一输入过旧版本 / 新版本（或两套配置），diff 输出。适合「升级后就坏了」。
10. **HITL bash 脚本** —— 最后手段。确实需要人点时，用脚本驱动**人**：每步打印该做什么、抓回他贴的输出，让循环仍然是结构化的。抓到的输出回流给你。
