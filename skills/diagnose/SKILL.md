# Diagnose

修 bug 的纪律。原则只有一条：**没有证据不下结论**。跳过任何阶段都要说明理由。读 `CONTEXT.md`（若有）对齐用词与已拍板决策。

**成因已在证据里时走捷径。** 报错讯息直接指到出错行、配置 / 依赖版本 / 拼写错这类一眼可核对的成因——证据已经完成定位，不需要建循环，直接跳到 Phase 5。捷径的判据是「**证据已定位成因**」（stack trace 指到的那行确实就是错的），不是「bug 看起来简单」；且捷径**只跳过定位、不跳过验证**——修复仍要一条先红后绿的命令（往往就是复现那个报错本身）。核对后发现指到的行没问题？那成因不在证据里，回到 Phase 1。

## Redact

本 skill 要贴命令、输出与抓到的 artifact。**先脱敏**：密钥、token、cookie、个人信息一律换成 `<REDACTED>`。循环用环境变量读凭据，别把它写进要展示的内容；HAR / 日志只引带信号的那几行。脱敏后的输出不足以定位时，说明缺什么并问用户。

## Phase 1 — 建反馈循环

**这一阶段就是本 skill 的全部**，其余都是机械劳动。有一个能对着**这个** bug 变红的 tight 信号，你就能找到原因——二分、验假设、下探针都只是消耗它；没有，盯着代码看再久也没用。

**在这里不成比例地多花时间。要主动、要有创造力、不许放弃。**

构造方式按这个顺序试：**失败测试**（在能碰到 bug 的任意 seam 上）→ **curl / HTTP 脚本**打本地服务 → **CLI 调用**喂 fixture、stdout 与已知good快照 diff → **headless 浏览器脚本**驱动 UI 断言 DOM/console/network。这四种不行时看 [references/feedback-loops.md](references/feedback-loops.md)（重放 trace、一次性 harness、fuzz、bisect 探测、差分、HITL 脚本）。

拿到**一个**循环后，**把它当产品来 tighten**：能更快吗（缓存 setup、跳过无关初始化、缩小测试范围）？信号能更锐吗（断言那个具体症状，不是「没崩」）？能更确定吗（钉住时间、播种 RNG、隔离文件系统、冻结网络）？30 秒的 flaky 循环几乎等于没有循环；2 秒的确定性循环是超能力。

非确定性 bug 的目标**不是干净复现，而是提高复现率**：触发点循环 100 次、并行、加压、收窄时序窗口、注入 sleep。50% 的抖动可以调，1% 不行——一直抬到能调为止。

**Completion —— 一个已经变过红的 tight 循环。** 你能说出**一条命令**（脚本路径、测试调用、curl），**已经真跑过至少一次**并贴出调用与（脱敏的）输出，且四条全中：

- [ ] **red-capable** —— 跑的是真实 bug 代码路径，断言的是**用户描述的那个**症状，所以它能因这个 bug 变红、修好后变绿。不是「跑起来没报错」，而是**能抓住这个 bug**。
- [ ] **确定性** —— 每次跑结论一致（抖动型：已钉住的高复现率）。
- [ ] **快** —— 秒级，不是分钟级。
- [ ] **agent 可跑** —— 你能无人值守地跑它。

**发现自己在这条命令存在之前就去读代码编理论时，停下**——直接跳到假设正是本 skill 要防的那个失败。没有 red-capable 命令，不进 Phase 2。真建不出来时明说，列出试过什么，并向用户要：能复现的环境访问权、一份脱敏 artifact（HAR、日志、core dump、带时间戳的录屏），或临时加生产探针的许可。**不带循环就往下假设是不允许的。**

## Phase 2 — 复现 + 最小化

跑循环，看它变红。确认：红的是**用户描述的那个**症状，不是旁边碰巧的另一个（错 bug = 错修）；多次运行都能复现（抖动型：复现率高到够调）；症状已抓下来（报错文本、错误输出、慢的耗时），供后面阶段验证修复真的对上了它。

然后**最小化**：删输入、调用方、配置、数据、步骤，**一次删一个，每次重跑**。Completion: 剩下的每个元素都是承重的——再删任何一个，循环就变绿。最小 repro 缩小 Phase 3 的假设空间，并且它本身就是 Phase 5 那个干净的回归测试。复现且最小化之前不往下走。

## Phase 3 — 假设

先生成 **3–5 条排好序**的假设，**再去验任何一条**——只生成一条会让你锚定在第一个看起来合理的想法上。每条必须**可证伪**，写成预测：

> 若 \<X\> 是原因，则改 \<Y\> 会让 bug 消失 / 改 \<Z\> 会让它更严重。

说不出预测的是 vibe，丢掉或磨锐。**排好序先给用户看**——他们常能一眼重排（「我们刚给 #3 上了个改动」）或告诉你哪条已排除，很便宜的检查点。不阻塞：AFK 就按你的排序继续。

## Phase 4 — 探针

每个探针对应 Phase 3 的某条具体预测，**一次只改一个变量**。工具优先级：debugger / REPL 检查（一个断点胜十条 log）→ 能区分假设的边界上打定向 log → 永不「全量 log 然后 grep」。

**每条调试 log 打唯一前缀**如 `[DEBUG-a4f2]`，清场就是一次 grep：没打标的会活下来，打了标的才死得干净。

性能回归走另一条：log 通常是错的工具。先建基线测量（计时 harness、`performance.now()`、profiler、查询计划）再二分。先量，后修。

## Phase 5 — 修 + 回归测试

回归测试写在修之前——**但只在存在正确 seam 时**。正确 seam = 测试能复现 call site 上**真实的 bug 形态**；只有太浅的 seam 时（bug 需要多个调用方却只能写单调用方测试、单测复现不出触发它的那条链），在那儿写回归测试给的是假安全感。seam 判据见 `/tdd`。

**不存在正确 seam 时，这件事本身就是发现**：记下来——是架构在阻止这个 bug 被锁死，交 Phase 6 处理。

存在时：把最小 repro 变成该 seam 上的失败测试 → 看它红 → 应用修复 → 看它绿 → 拿 Phase 1 的循环重跑**未最小化的原始**场景。

## Completion

逐条勾完才算完成：

- [ ] 原 repro 不再复现（重跑 Phase 1 的循环，贴出输出）
- [ ] 回归测试通过，或「无正确 seam」已明确记录
- [ ] 所有 `[DEBUG-` 探针已清（grep 前缀确认）
- [ ] 一次性 harness 与循环脚本已删，或移到明确标注的调试位置
- [ ] 最终成立的那条假设写进 commit / PR 讯息（Commit 仅在用户明确要求时做）——下一个 debugger 靠它学到东西

**修完之后**再问：什么本可以预防这个 bug？此刻信息比开工时多。答案落在架构上（没有好的测试 seam、调用方纠缠、隐藏耦合）时交 `/breakdown` 开 slice，别在这条里顺手重构。收尾输出一行 handoff：

```
下一步：/code-review · <工作区 diff 或定点> · 已修「<症状>」，成立的假设是「<一句>」
```
